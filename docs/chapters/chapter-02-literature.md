# บทที่ 2: เอกสารและทฤษฎีที่เกี่ยวข้อง

บทนี้รวบรวมแนวคิด ทฤษฎี มาตรฐาน และเทคโนโลยีหลักที่ใช้เป็นรากฐานในการออกแบบและพัฒนาโครงงานระบบวิเคราะห์ความต้องการทักษะในตลาดแรงงานไทยจากประกาศงาน ได้แก่ สถาปัตยกรรมคลังข้อมูล (Data Warehouse) กระบวนการ ETL และกรอบคุณภาพข้อมูล การประมวลผลภาษาไทย (Thai NLP) และอนุกรมวิธานทักษะ การเรียนรู้ของเครื่องสำหรับการประมาณการเงินเดือน กฎหมายลิขสิทธิ์และข้อมูลส่วนบุคคล ตลอดจนเทคโนโลยีเว็บแอปพลิเคชันและการแสดงผลข้อมูล

---

## 2.1 การวิเคราะห์ความต้องการทักษะในตลาดแรงงาน (Labor Market & Skill Demand Intelligence)

การวิเคราะห์ข่าวกรองตลาดแรงงาน (Labor Market Intelligence: LMI) จากข้อมูลประกาศรับสมัครงานออนไลน์เป็นการใช้ข้อมูลทุติยภูมิที่องค์กรเผยแพร่เพื่อสรรหาบุคลากรมาสกัดเป็นตัวชี้วัดเชิงปริมาณด้านตำแหน่งงาน ทักษะที่ต้องการ พื้นที่ และค่าตอบแทน ข้อได้เปรียบสำคัญเมื่อเทียบกับการสำรวจด้วยแบบสอบถามแบบดั้งเดิมคือ ความทันต่อสถานการณ์ (Timeliness) และความละเอียดในระดับทักษะเฉพาะทาง (Skill Granularity)

อย่างไรก็ตาม การใช้ข้อมูลประกาศงานออนไลน์มีข้อจำกัดเชิงระเบียบวิธีที่ต้องตระหนักในการตีความ ได้แก่:
1. **ไม่ใช่อัตราการจ้างงานจริงทั้งหมด (Sample vs. Census):** ตำแหน่งงานระดับบริหาร ตำแหน่งผ่านเครือข่ายบุคคล หรือแรงงานนอกระบบมักไม่ปรากฏบนกระดานหางานออนไลน์
2. **ลักษณะข้อมูลแบบภาพตัดขวางตามช่วงเวลา (Snapshot Window):** ประกาศที่พบในวันเก็บข้อมูลคือประกาศที่ยังเปิดรับสมัครอยู่ในช่วงเวลานั้น การติดตามอายุของประกาศจึงอาศัยการตรวจสอบซ้ำเป็นรอบสัปดาห์ (`first_seen` และ `last_seen`) เพื่อแยกประกาศใหม่และประกาศที่ยังคงเปิดอยู่
3. **อคติจากการเลือกเปิดเผยข้อมูล (Selection Bias):** โดยเฉพาะข้อมูลเงินเดือนที่นายจ้างจำนวนหนึ่งเลือกไม่ระบุเป็นตัวเลข (จากผลสำรวจตัวอย่างพบราวร้อยละ 44) ดังนั้นแบบจำลองและการวิเคราะห์เงินเดือนจึงสะท้อนเฉพาะกลุ่มประชากรย่อยที่เปิดเผยตัวเลขเงินเดือนเท่านั้น

## 2.2 ทฤษฎีคลังข้อมูล (Data Warehouse: Star Schema และ Galaxy Schema)

ตามแนวคิด Dimensional Modeling ของ Kimball คลังข้อมูลมุ่งเน้นการแยกข้อมูลออกเป็น **ตารางข้อเท็จจริง (Fact Table)** ที่เก็บเหตุการณ์หรือค่าที่ใช้วัดเชิงปริมาณ และ **ตารางมิติ (Dimension Table)** ที่เก็บคำอธิบายบริบทเพื่อรองรับการกรอง การจัดกลุ่ม และการรวมยอด (Aggregation) ได้รวดเร็ว

### 2.2.1 Star Schema และ Galaxy Schema (Fact Constellation)
- **Star Schema:** ประกอบด้วยตาราง Fact ตรงกลาง 1 ตาราง ล้อมรอบด้วยตาราง Dimension ที่ไม่แตกย่อยหลายชั้น (Denormalized) เพื่อให้การสืบค้นเชิงวิเคราะห์ (OLAP) ใช้คำสั่ง `JOIN` น้อยลง
- **Galaxy Schema (Fact Constellation):** เป็นการขยาย Star Schema ให้มี Fact Table มากกว่า 1 ตารางที่ใช้ตารางมิติเดียวกันร่วมกัน (**Conformed Dimensions**) โครงงานนี้เลือกใช้ Galaxy Schema ใน schema `dw` โดยให้ตารางมิติหลัก (`dim_date`, `dim_location`, `dim_occupation`, `dim_skill`, `dim_company`, `dim_source`) เชื่อมโยงร่วมกันระหว่าง Fact Table 3 ตารางที่มีระดับความละเอียด (Grain) ต่างกัน ได้แก่:
  1. `dw.fact_job_posting` (Grain = 1 ประกาศงานล่าสุด)
  2. `dw.fact_posting_skill` (Grain = 1 ประกาศงาน × 1 ทักษะที่พบ)
  3. `dw.fact_labor_monthly` (Grain = 1 เดือน × 1 ตัวชี้วัดบริบทแรงงานภาครัฐ)

### 2.2.2 สถาปัตยกรรมฐานข้อมูลแบบหลายชั้น (Multi-Layer Data Architecture)
การแบ่ง Schema ออกเป็นชั้นหน้าที่ที่ชัดเจนช่วยลดความซับซ้อนและเพิ่มความปลอดภัยของข้อมูล ได้แก่
- **`staging`:** พื้นที่พักข้อมูลที่แยกโครงสร้างจากไฟล์ HTML ดิบแล้ว (ตัด PII ออกแล้ว) พร้อมเก็บประวัติการดึงข้อมูล (`scrape_run`, `listing_seen`) และผลตรวจคุณภาพข้อมูล (`dq_result`)
- **`dw`:** คลังข้อมูลหลักแบบ Star/Galaxy ที่ทำความสะอาดและกำหนด Surrogate Key แล้ว
- **`mart`:** ตารางและ View สรุปผลเชิงสถิติ (Pre-aggregated Data Marts) ที่สร้างขึ้นเฉพาะสำหรับหน้าเว็บ โดยผ่านการซ่อนกลุ่มที่มีจำนวนตัวอย่างน้อย (`n < 5`)
- **`ml`:** ชั้นจัดเก็บผลการทดลองและเปรียบเทียบแบบจำลอง ML (`experiment`, `model_result`, `feature_importance`)
- **`public`:** ตารางข้อมูลส่วนบุคคลของผู้ใช้งานแอปพลิเคชัน (`app_*`) ที่ป้องกันด้วย Row Level Security (RLS)

## 2.3 กระบวนการ ETL การสุ่มตัวอย่างแบบแบ่งชั้น และคุณภาพข้อมูล

### 2.3.1 กระบวนการ ETL แบบ Idempotent
ETL (Extract–Transform–Load) ที่มีคุณสมบัติ **Idempotent** หมายถึงกระบวนการที่สามารถสั่งรันซ้ำได้หลายครั้งบนชุดข้อมูลเดิมหรือชุดข้อมูลที่มีการอัปเดตโดยไม่ทำให้เกิดแถวซ้ำในคลังข้อมูล โดยอาศัยรหัสอ้างอิงเฉพาะ (`(source, source_job_id)` และ `content_hash` SHA-256) ร่วมกับคำสั่ง `UPSERT` (`ON CONFLICT DO UPDATE`)

### 2.3.2 การสุ่มแบบแบ่งชั้นและค่าน้ำหนัก (Stratified Sampling & Sample Weight)
เนื่องจากปริมาณประกาศงานในประเทศไทยกระจุกตัวสูงในกรุงเทพมหานครและเขตอุตสาหกรรมภาคตะวันออก (จากการสำรวจเบื้องต้น กรุงเทพฯ คิดเป็นร้อยละ 36.8 ขณะที่ 14 จังหวัดภาคใต้รวมกันมีเพียงร้อยละ 2.4) หากสุ่มเท่ากันทุกจังหวัดจะทำให้ตัวเลขระดับประเทศเอียงไปทางจังหวัดเล็ก แต่หากสุ่มตามสัดส่วนอย่างเดียวจังหวัดเล็กจะไม่มีตัวอย่างเพียงพอสำหรับการวิเคราะห์

โครงงานจึงใช้ **การสุ่มแบบแบ่งชั้น (Stratified Sampling)** แบ่งชั้น $h$ ตามจังหวัด × หมวดอาชีพ และจัดสรรขนาดตัวอย่างแบบ **Proportional Allocation with Minimum Floor**:
$$n_h = \min\Big(N_h,\; \max\big(5,\; \operatorname{round}(n_{\text{target}} \cdot \frac{N_h}{N_{\text{total}}})\big)\Big)$$
โดย $N_h$ คือจำนวนประกาศทั้งหมดที่พบในชั้น $h$ (`staging.listing_seen`) และ $n_h$ คือจำนวนตัวอย่างที่เก็บจริง แล้วคำนวณค่าน้ำหนักประชากรประจำแต่ละแถว:
$$w_h = \frac{N_h}{n_h}$$
ค่าน้ำหนักนี้ทำให้ผลรวมน้ำหนักในชั้น $h$ เท่ากับขนาดประชากรของชั้นพอดี ($\sum_{i \in h} w_i = N_h$) และเมื่อคำนวณสัดส่วนความต้องการทักษะในระดับภาคหรือระดับประเทศในชั้น `mart` จะใช้ค่าเฉลี่ยถ่วงน้ำหนัก $\frac{\sum w_i \cdot \mathbb{I}[\text{มีทักษะ}_i]}{\sum w_i}$ เพื่อชดเชยความเอียงจากการสุ่ม

### 2.3.3 มิติคุณภาพข้อมูล (Data Quality Dimensions)
การประเมินคุณภาพข้อมูลในโครงงานอ้างอิงกรอบมาตรฐาน 8 ด้าน ได้แก่:
1. **Completeness:** ความครบถ้วนของฟิลด์สำคัญ (ตำแหน่ง, จังหวัด, หมวดงาน, เงินเดือน, ทักษะ)
2. **Validity:** ความถูกต้องตามขอบเขตค่าและรูปแบบ (เช่น `salary_min <= salary_max`, เงินเดือน 5,000–500,000 บาท/เดือน, ชื่อจังหวัดตรง 77 จังหวัด)
3. **Uniqueness:** อัตราการซ้ำของรหัสประกาศและเนื้อหาซ้ำต่างรหัส
4. **Consistency:** ความสอดคล้องข้ามฟิลด์ (เช่น หมวดงานกับกลุ่มอาชีพ, การรวมชื่อบริษัทหลัง normalize)
5. **Freshness:** ความทันสมัยของข้อมูลและสัดส่วนประกาศที่หมดอายุแล้ว
6. **Taxonomy Coverage & Precision:** สัดส่วนประกาศที่สกัดทักษะได้ ≥ 1 ทักษะ และความแม่นยำจากการตรวจโดยมนุษย์
7. **Compliance:** การตรวจสอบว่าไม่มีคอลัมน์ข้อมูลผู้ติดต่อ HR และไม่มีตัวแปรเพศ/อายุในชุดข้อมูล ML
8. **Sampling Conservation:** ความสอดคล้องของผลรวม `sample_weight` เทียบกับ `N_h` ในแต่ละชั้น

## 2.4 การประมวลผลภาษาไทย (Thai NLP) และอนุกรมวิธานทักษะ

### 2.4.1 การตัดคำภาษาไทยด้วย PyThaiNLP (`newmm`)
ภาษาไทยไม่มีสัญลักษณ์เว้นวรรคเพื่อแยกคำอย่างชัดเจนเหมือนภาษาอังกฤษ จึงต้องใช้ตัวตัดคำ (Tokenizer) ก่อนการวิเคราะห์ข้อความ ไลบรารี **PyThaiNLP** มีอัลกอริทึม **`newmm`** (New Maximum Matching) ซึ่งเป็นวิธีแบบ Dictionary-based ที่ค้นหาการแบ่งคำที่ให้จำนวนคำน้อยที่สุดโดยใช้หลัก Dictionary + Graph Search (BFS) ร่วมกับ TCC (Thai Character Clusters) เพื่อให้ไม่ตัดขาดกลางพยางค์ อัลกอริทึมนี้มีความเร็วสูง ทำงานแบบ Deterministic (ผลลัพธ์คงที่เมื่อรันซ้ำ) และไม่ใช้ทรัพยากร GPU

### 2.4.2 การสกัดทักษะด้วย Dictionary + Alias และกฎ Word Boundary
การใช้ Dictionary + Alias (`canonical skill` + คำพ้องไทย/อังกฤษ/คำสะกดผิด) ให้ผลลัพธ์ที่อธิบายได้ (Explainable) และตรวจสอบข้อผิดพลาดรายทักษะได้ตรงไปตรงมา สำหรับคำภาษาอังกฤษที่สั้นหรือกำกวม เช่น `R`, `C`, `Go`, `Word`, `SQL` จำเป็นต้องใช้ขอบเขตคำ (`\bword\b` หรือ boundary assertion ที่ไม่ติดตัวอักษร/ตัวเลข) เพื่อไม่ให้จับคำอื่นผิดพลาด (เช่น ไม่จับ `Word` จากคำว่า `Password` หรือ `Keyword`) ส่วนภาษาไทยใช้การจับคู่ร่วมกับ token จาก `newmm` และบริบทที่กำหนด

### 2.4.3 มาตรฐานทักษะสากล O*NET, ESCO และ Trigram Similarity (`pg_trgm`)
- **O*NET 31.0 (CC BY 4.0):** ระบบจำแนกอาชีพและทักษะของกระทรวงแรงงานสหรัฐอเมริกา มีรายการซอฟต์แวร์และเทคโนโลยีมากกว่า 31,000 แถว ใช้เป็นรหัสอ้างอิงชื่อมาตรฐานสากล (`onet_ref`)
- **ESCO (European Skills, Competences, Qualifications and Occupations):** กรอบทักษะมาตรฐานของสหภาพยุโรป ใช้เป็นรหัสอ้างอิง (`esco_ref`) เสริมในฝั่งทักษะเชิงวิชาชีพ
- **Trigram Similarity (`pg_trgm`):** เพื่อช่วยขยายคำพ้องทักษะใหม่จากคำที่พบบ่อยในประกาศแต่ยังไม่อยู่ในพจนานุกรม ระบบใช้การเทียบความคล้ายของสตริงแบบ 3-gram (เช่น Jaccard/Dice similarity โดยตั้งเกณฑ์ $\ge 0.4$) ใน SQL และ Python ซึ่งเป็นวิธีเชิงกฎ (Rule-based) ที่โปร่งใสโดยไม่พึ่งพา LLM

### 2.4.4 การวัดความแม่นยำและความสอดคล้องของผู้ประเมิน (Precision, Recall และ Cohen's Kappa)
สำหรับการตรวจประเมินชุดข้อมูลตัวอย่าง 200 ประกาศโดยมนุษย์ ใช้ค่าชี้วัด Precision, Recall (นับเฉพาะทักษะที่อยู่ในขอบเขต Taxonomy พร้อมบันทึกรายการนอก Taxonomy แยกต่างหาก) และ F1-Score และกรณีมีผู้ตรวจประเมินตั้งแต่ 2 คนขึ้นไปบนชุดซ้ำ 50 ประกาศ จะคำนวณสัมประสิทธิ์ความสอดคล้อง **Cohen's Kappa ($\kappa$)**:
$$\kappa = \frac{p_o - p_e}{1 - p_e}$$
โดย $p_o$ คือสัดส่วนการตัดสินใจที่ตรงกันจริง และ $p_e$ คือสัดส่วนความบังเอิญที่จะตรงกันโดยสุ่ม ค่า $\kappa \ge 0.60$ แสดงถึงความสอดคล้องระดับดี (Substantial agreement) ตามเกณฑ์ Landis & Koch

## 2.5 ทฤษฎีการเรียนรู้ของเครื่องสำหรับการประมาณการเงินเดือน

### 2.5.1 การแปลงตัวแปรเป้าหมาย (Log Transformation) และตัวชี้วัด Regression
เนื่องจากข้อมูลเงินเดือนมีลักษณะการกระจายตัวแบบเบ้ขวา (Right-skewed) การฝึกสอนโมเดลบนค่า $y' = \ln(\text{salary\_mid})$ ช่วยลดผลกระทบของค่าผิดปกติ (Outliers) ที่มีเงินเดือนสูงมาก และทำให้ความคลาดเคลื่อนเชิงสัมพัทธ์มีเสถียรภาพมากขึ้น ก่อนแปลงค่ากลับเป็นบาท ($\hat{y} = \exp(\hat{y}')$) เพื่อวัดผลเทียบกับเงินเดือนจริงด้วย 4 ตัวชี้วัดหลัก:
- **$R^2$ (Coefficient of Determination):** สัดส่วนความแปรปรวนของเงินเดือนที่โมเดลอธิบายได้
- **RMSE (Root Mean Squared Error):** ค่ารากที่สองของค่าเฉลี่ยความคลาดเคลื่อนกำลังสอง (ลงโทษความคลาดเคลื่อนสูงเป็นพิเศษ จึงใช้เป็นเกณฑ์หลักเลือก Champion)
- **MAE (Mean Absolute Error):** ค่าเฉลี่ยความคลาดเคลื่อนสัมบูรณ์ในหน่วยบาท อธิบายเข้าใจง่าย
- **MAPE (Mean Absolute Percentage Error):** ร้อยละความคลาดเคลื่อนสัมบูรณ์เฉลี่ย

### 2.5.2 แบบจำลอง 5 ตระกูลที่นำมาเปรียบเทียบ
1. **Ridge Regression:** แบบจำลองเชิงเส้นที่ใช้ Regularization แบบ $L_2$ ($\alpha \sum w_j^2$) เพื่อลดปัญหา Multicollinearity ของ feature ทักษะแบบ Multi-hot
2. **Random Forest:** แบบจำลอง Ensemble แบบ Bagging ที่สร้างต้นไม้ตัดสินใจหลายต้นจากการสุ่มตัวอย่างและสุ่ม feature แล้วหาค่าเฉลี่ย ช่วยลด Variance
3. **XGBoost (eXtreme Gradient Boosting):** Gradient Boosted Trees ที่ใช้ Second-order gradient, Regularization ใน objective function และการแบ่งโหนดอย่างมีประสิทธิภาพ
4. **LightGBM:** Gradient Boosted Trees ที่เติบโตแบบ Leaf-wise ร่วมกับเทคนิค Histogram binning ทำให้ฝึกสอนได้รวดเร็วและรองรับ feature จำนวนมากได้ดี
5. **CatBoost:** Gradient Boosted Trees ที่เด่นด้านการจัดการตัวแปรเชิงหมวดหมู่ (Categorical Features) ด้วย Ordered Target Statistics และใช้ Oblivious Trees (Symmetric Trees) ที่ทนต่อ Overfitting

### 2.5.3 การป้องกัน Data Leakage ด้วย GroupKFold และ Nested Cross-Validation
ในข้อมูลประกาศงาน บริษัทเดียวกันมักลงประกาศหลายตำแหน่งด้วยโครงสร้างค่าตอบแทนเดียวกัน หากสุ่มแบ่งข้อมูลแบบ K-Fold ทั่วไป ประกาศของบริษัทเดียวกันอาจอยู่ในทั้งชุด Train และ Validation ทำให้ผลประเมินดีเกินจริง โครงงานนี้จึงใช้ **`GroupKFold(5)` โดยจัดกลุ่มตาม `company_key`** เพื่อให้ประกาศทุกฉบับของบริษัทเดียวกันอยู่ภายใน fold เดียวเท่านั้น

นอกจากนี้ การเลือก Hyperparameter ที่ใช้ข้อมูล Validation ชุดเดียวกันกับการวัดผลสุดท้ายจะก่อให้เกิด Optimistic Bias โครงงานจึงใช้ **Nested Cross-Validation** โดยแบ่งชั้นนอกเป็น `GroupKFold(5)` เพื่อประเมินผลเป็นกลาง และใช้ `GroupKFold(3)` ชั้นในบนชุด Train ของแต่ละ fold เพื่อค้นหา Hyperparameter ที่เหมาะสม (Randomized Search ไม่เกิน 20 รอบ)

### 2.5.4 ช่วงค่าคาด (Prediction Interval) และการอธิบายผล
เพื่อไม่ให้ผู้ใช้เข้าใจผิดว่าค่าทำนายเป็นตัวเลขตายตัว โครงงานคำนวณช่วงประมาณการ $[p_{25}, p_{75}]$ จาก Quantile ของ Residual บน Validation predictions ($[\hat{y} + q_{0.25}, \hat{y} + q_{0.75}]$ หรือในสเกล log) และใช้ **Permutation Importance / SHAP** เพื่อแสดงปัจจัยและทักษะที่มีอิทธิพลต่อค่าประมาณการ

## 2.6 กรอบกฎหมาย จริยธรรม และความเป็นธรรมของระบบ

1. **เงื่อนไขการใช้งาน (Terms of Service) และ `robots.txt`:** การเก็บข้อมูลอัตโนมัติต้องเคารพไฟล์ `robots.txt` ของเจ้าของเว็บไซต์ ไม่เรียกใช้งาน API ภายในที่ไม่ได้เปิดสาธารณะ ไม่หลบเลี่ยงการจำกัดอัตรา (Rate Limiting) และในส่วนการเผยแพร่ต้องปฏิบัติตามข้อห้ามคัดลอกเผยแพร่ซ้ำโดยแสดงผลเฉพาะสถิติเชิงรวม (`n >= 5`) พร้อมลิงก์กลับไปยังต้นฉบับ
2. **พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562 (PDPA):** ข้อมูลชื่อบุคคล เบอร์โทรศัพท์ อีเมล และ LINE ID ของผู้ประสานงาน HR ถือเป็นข้อมูลส่วนบุคคล จึงต้องตัดทิ้งทันทีที่ขั้นตอน parse ส่วนข้อมูลผู้ใช้งานระบบเว็บ (ทักษะ หลักสูตร บัญชีผู้ใช้) ต้องเก็บเท่าที่จำเป็น (Data Minimization) จำกัดสิทธิ์การเข้าถึงด้วย Row Level Security (RLS) และเปิดโอกาสให้ผู้ใช้ลบข้อมูลของตนเองได้
3. **ความเป็นธรรมของอัลกอริทึม (Algorithmic Fairness):** ประกาศงานในไทยจำนวนไม่น้อยยังระบุข้อกำหนดเรื่องเพศ (27% ในตัวอย่างเบื้องต้น) และอายุ (58%) การนำคุณลักษณะเหล่านี้เข้าเป็น feature ในแบบจำลองประมาณการเงินเดือนจะผลิตซ้ำอคติทางเพศและอายุ โครงงานจึงกำหนดเป็นกติกาเหล็กให้ตัด `gender`, `age` และ `company_name` ออกจากชุด feature ของ ML โดยเด็ดขาด

## 2.7 เทคโนโลยีเว็บแอปพลิเคชัน การออกแบบ Liquid Glass และ Grounded AI Chat

1. **สถาปัตยกรรม Web & Serving:**
   - **Next.js (App Router, TypeScript):** ใช้ Server Components ดึงข้อมูลจาก `mart.*` โดยตรงผ่าน Supabase client ฝั่งเซิร์ฟเวอร์ และใช้ API Route Handler เป็น BFF Proxy (`/api/salary/estimate` และ `/api/chat`) เพื่อไม่เปิดเผย Key ลับสู่เบราว์เซอร์
   - **Supabase (PostgreSQL + Auth + RLS):** จัดการฐานข้อมูลหลาย schema และบังคับนโยบาย RLS ระดับแถวในฐานข้อมูล
   - **FastAPI (`services/ml-api`):** ให้บริการโมเดล Champion ด้วย Python โดยตรง (joblib/native model) ช่วยหลีกเลี่ยงความเสี่ยงจากข้อจำกัดขนาดและ runtime ของ Serverless Function เมื่อแปลงเป็น ONNX
2. **หลักการออกแบบ Liquid Glass และ Data Visualization Accessibility:**
   - ใช้สไตล์ Liquid Glass (พื้นหลังโปร่งแสง `backdrop-filter: blur()` ขอบสว่างบาง) เฉพาะส่วนเปลือกโครงสร้าง (Sidebar, Top Bar, กรอบการ์ด) ส่วนพื้นที่แสดงกราฟและตารางวางบนพื้นทึบ (`--surface-chart` ความทึบ 94%) เพื่อให้ค่าความเปรียบต่าง (Contrast Ratio) ผ่านเกณฑ์ **WCAG 2.1 AA ($\ge 4.5:1$)** เสมอ พร้อมกลไกปิดความโปร่งใส (`data-glass="off"`, `prefers-reduced-transparency`)
   - ใช้ **Apache ECharts** คู่กับ **TanStack Table** โดยยึดกฎสร้างกราฟมาตรฐาน: ห้ามใช้แกนคู่ (Dual-axis), ผูกสีตามตัวตนข้อมูล (`#6C5CE7` = ฉัน/หลักสูตร, `#E0623F` = ตลาด, `#0E9AAE` = ค่าเปรียบเทียบ) ที่ผ่านการตรวจสอบตาบอดสี (CVD), และบังคับมีปุ่ม "ดูเป็นตาราง" ในทุกกราฟ
3. **ผู้ช่วยแชท AI แบบจำกัดบริบท (Grounded Context Chat):**
   - แทนที่จะให้ LLM สร้างคำสั่ง SQL โดยตรง (**Text-to-SQL**) ซึ่งเสี่ยงต่อการเจาะระบบ การดึงข้อมูลผิด schema หรือการแปลความหมายคลาดเคลื่อน โครงงานเลือกส่งสรุปข้อมูลที่ปรากฏบนหน้าเว็บปัจจุบัน (**`pageContext`**) ให้ Google Gemini ผ่าน System Prompt ที่กำกับให้ตอบเฉพาะจากตัวเลขในบริบทนั้นและห้ามคำนวณหรือแต่งตัวเลขใหม่ ช่วยลดปัญหา Hallucination และตรวจสอบความถูกต้องย้อนกลับได้ง่าย
