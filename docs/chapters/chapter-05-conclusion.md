# บทที่ 5: สรุปผล อภิปรายผล ข้อจำกัด และข้อเสนอแนะ

---

## 5.1 สรุปผลการดำเนินงานตามวัตถุประสงค์

โครงงาน **"Skill Demand Intelligence: ระบบวิเคราะห์ความต้องการทักษะในตลาดแรงงานไทยจากประกาศงาน ด้วยคลังข้อมูลและการเรียนรู้ของเครื่อง"** (*หัวข้อ E′*) ได้ดำเนินงานครบถ้วนตามวัตถุประสงค์ทั้ง 5 ประการ ดังนี้

1. **ด้านการเก็บ คลีน และจัดโครงสร้างคลังข้อมูล:** พัฒนาระบบ Polite Scraper (`pipeline/scraper/`) ที่เก็บตัวอย่างประกาศงานแบบแบ่งชั้นจังหวัด × หมวด (พร้อม `sample_weight` และ Re-discovery รายสัปดาห์) ตัดข้อมูลผู้ติดต่อ HR ตั้งแต่ขั้น Parse และเชื่อมโยงเข้าสู่กระบวนการ ETL แบบ Idempotent สู่คลังข้อมูลแบบ Star/Galaxy (`staging` → `dw` → `mart`) พร้อมการตรวจสอบคุณภาพข้อมูลอัตโนมัติ 8 ด้าน (`[อัปเดตจำนวนประกาศจริงและอัตราความครบถ้วนหลัง T1.8]`)
2. **ด้านอนุกรมวิธานทักษะและการสกัดทักษะภาษาไทย/อังกฤษ:** สร้าง Taxonomy ทักษะของโครงงานเองพร้อมคำพ้องไทย/อังกฤษ (`taxonomy/skills.csv`, `aliases.csv`, `occupations.csv`) อ้างอิงรหัสมาตรฐานสากล O*NET และ ESCO ร่วมกับการตัดคำด้วย `PyThaiNLP newmm` กฎ Word Boundary และคิวเสนอ alias แบบ Rule-based ด้วย `pg_trgm` (`[อัปเดตผล Precision/Recall จากชุดตรวจมือ 200 ประกาศ T2.7]`)
3. **ด้านเว็บแอปพลิเคชันสำหรับผู้ใช้ 3 กลุ่ม:** พัฒนาเว็บแอปพลิเคชัน Next.js สไตล์ Liquid Glass และ Apache ECharts ที่แสดงเฉพาะสถิติรวม (`n >= 5`) คู่กับลิงก์ประกาศต้นฉบับ รองรับการใช้งานของนักศึกษา (Market Explorer, My Skills, Skill Gap, Salary Estimator), สถานศึกษา (Curriculum Alignment), และผู้ดูแลระบบ (Pipeline, Data Quality, Taxonomy Review) พร้อมผู้ช่วยแชท Gemini ที่ตอบเฉพาะข้อมูลบนหน้า (`pageContext`) และระบบสิทธิ์ RLS บน Supabase
4. **ด้านการเปรียบเทียบโมเดล ML และให้บริการจริง:** พัฒนา ML Pipeline ที่ตัดตัวแปรอ่อนไหว (`gender`, `age`, `company_name`) ออกอย่างเด็ดขาด เปรียบเทียบ 5 โมเดล + Baseline ด้วย `GroupKFold(5)` และ Nested `GroupKFold(3)` และนำโมเดลที่ชนะ (`[อัปเดตชื่อโมเดล Champion และ RMSE/MAE]`) เพียงตัวเดียวมาให้บริการผ่าน FastAPI `services/ml-api` คู่กับตาราง Fallback `mart.salary_prediction`
5. **ด้านการประเมินประสิทธิภาพและความพึงพอใจ:** ดำเนินการทดสอบฟังก์ชัน (F1–F9), ความปลอดภัย RLS, Grounded Chat Check 30 คำถาม, ประสิทธิภาพการโหลดหน้าเว็บ, และเก็บแบบสอบถามความพึงพอใจ Likert 5 ระดับ (`[อัปเดตผลคะแนนเฉลี่ยและระดับความพึงพอใจหลัง T8.3]`)

## 5.2 อภิปรายผลการดำเนินงาน

1. **ความจำเป็นของ Skill Taxonomy สองภาษาและการจับคู่แบบมีขอบเขตคำ:**  
   ผลการสำรวจเบื้องต้นยืนยันว่าการใช้ชื่อทักษะมาตรฐานจาก O*NET โดยตรงไม่สามารถจับคู่กับประกาศงานไทยได้อย่างครอบคลุม (ตรงแบบเป๊ะเพียง 5/21 ประกาศ) และ ESCO ไม่รองรับภาษาไทย การสร้าง Taxonomy ที่มีคำพ้องไทย/อังกฤษ/คำสะกดผิดที่พบจริง ร่วมกับการใช้ `word_boundary` สำหรับคำสั้นกำกวมและการตรวจมือ 200 ประกาศ เป็นปัจจัยหลักที่ทำให้การวัดความต้องการทักษะมีความแม่นยำและสามารถตรวจสอบย้อนกลับได้ โดยไม่จำเป็นต้องพึ่งพา LLM ที่คาดเดาผลได้ยากกว่าและมีต้นทุนสูง
2. **ความสำคัญของการสุ่มแบบแบ่งชั้นและค่าน้ำหนัก (`sample_weight`):**  
   เนื่องจากประกาศงานบน JobThai กว่าร้อยละ 36.8 อยู่ในกรุงเทพมหานคร และจังหวัดอุตสาหกรรมภาคตะวันออกมีสัดส่วนสูง ขณะที่ 14 จังหวัดภาคใต้มีเพียงร้อยละ 2.4 การสุ่มแบบแบ่งชั้นโดยกำหนดขั้นต่ำชั้นละ 5 ประกาศทำให้จังหวัดขนาดเล็กยังมีข้อมูลเพียงพอสำหรับการวิเคราะห์รายพื้นที่ ในขณะที่การเก็บค่า `sample_weight = N_h / n_h` ช่วยให้การรวมยอดระดับภาคและระดับประเทศไม่บิดเบือนไปตามจำนวนตัวอย่างที่สุ่มเกินสัดส่วนในจังหวัดเล็ก
3. **การออกแบบ ML อย่างเป็นธรรมและปราศจากการรั่วไหลของข้อมูล (Fairness & No Data Leakage):**  
   การพบว่าประกาศงานระบุเพศถึงร้อยละ 27 และอายุถึงร้อยละ 58 สะท้อนว่าการนำข้อความดิบทั้งหมดเข้าโมเดลโดยไม่คัดกรองอาจผลิตซ้ำอคติทางเพศและอายุได้ การแยกบริษัทด้วย `GroupKFold` และการปรับจูนด้วย Nested `GroupKFold` ช่วยป้องกันไม่ให้โมเดลจำโครงสร้างเงินเดือนของบริษัทเดิมข้ามชุด Train/Test ทำให้ตัวชี้วัด `RMSE` และ `MAE` สะท้อนความสามารถในการคาดการณ์ทั่วไปได้สมจริงยิ่งขึ้น
4. **ความสมดุลระหว่างความสวยงามของ Liquid Glass และความน่าเชื่อถือของข้อมูล (Data Integrity):**  
   หลักการ *"แก้วเฉพาะเปลือก กราฟและข้อความอยู่บนพื้นทึบ"* (`--surface-chart` ความทึบ 94%) ช่วยให้ได้ความสวยงามทันสมัยโดยไม่สูญเสียความคมชัด (Contrast ≥ 4.5:1) และการแสดงช่วงเงินเดือน `p25–p75` แทนตัวเลขเดี่ยว รวมถึงการบังคับแชท Gemini ให้อ้างอิงเฉพาะ `pageContext` ช่วยลดความเสี่ยงที่ผู้ใช้จะเข้าใจตัวเลขประมาณการคลาดเคลื่อน

## 5.3 ข้อจำกัดของโครงงาน (Limitations)

การนำผลวิเคราะห์และค่าประมาณการจากระบบไปใช้อ้างอิงต้องคำนึงถึงข้อจำกัดเชิงระเบียบวิธีที่สำคัญ 5 ประการ (ตามข้อกำหนดใน `PLAN.md §6`, `CONTEXT.md §5.4` และ `docs/data-spike-2026-11-18.md`) ดังนี้

1. **อคติจากการเลือกเปิดเผยเงินเดือน (Selection Bias):** มีเพียงประมาณร้อยละ 56 ของประกาศงานที่ระบุเงินเดือนเป็นตัวเลข ส่วนที่เหลือระบุเป็น "ตามตกลง" หรือ "ตามโครงสร้างบริษัท" ซึ่งประกาศที่ระบุตัวเลขมักเอนเอียงไปทางตำแหน่งงานระดับต้น งานฝ่ายขาย หรืองานปฏิบัติการมากกว่าตำแหน่งระดับบริหารหรือผู้เชี่ยวชาญเฉพาะทางระดับสูง
2. **เงินเดือนประกาศไม่ใช่เงินเดือนที่ได้รับจริง (Posted Salary ≠ Actual Compensation):** ตัวเลขเงินเดือนในประกาศเป็นเพียงกรอบฐานเงินเดือนที่นายจ้างเสนอเบื้องต้น ยังไม่รวมค่าคอมมิชชัน ค่าล่วงเวลา โบนัส สวัสดิการ หรือผลของการเจรจาต่อรองจริงหลังสัมภาษณ์
3. **ชุดข้อมูลเป็นกลุ่มตัวอย่าง ไม่ใช่สำมะโนประชากร (Sample, Not Census):** ข้อมูลมาจากกระดานหางานออนไลน์หลัก (JobThai) ด้วยการสุ่มแบบแบ่งชั้น ไม่ได้ครอบคลุมตำแหน่งงานทั้งหมดในตลาดแรงงานไทย (เช่น การสรรหาผ่านเครือข่าย งานราชการเต็มรูปแบบ หรือแรงงานนอกระบบ)
4. **กรอบเวลาแบบภาพตัดขวางระยะสั้น (3–4 เดือน Snapshot Window):** เนื่องจากระยะเวลาโครงงานครอบคลุมการเก็บข้อมูลประมาณ 3–4 เดือน และ JobThai ไม่ระบุวันหมดอายุของประกาศในโครงสร้างข้อมูล แนวโน้มที่แสดงจึงเป็นความเคลื่อนไหว **รายสัปดาห์** ของประกาศที่ยังเปิดอยู่ ณ รอบ Re-discovery ไม่สามารถใช้อ้างอิงวัฏจักรฤดูกาลรายปีหรือพยากรณ์ตลาดระยะยาวได้
5. **ขอบเขตของอนุกรมวิธานทักษะและการตัดตัวแปรอ่อนไหว:** ทักษะใหม่เฉพาะกลุ่มที่ยังไม่ถูกอนุมัติเข้า Taxonomy จะยังไม่ถูกนับจนกว่าผู้ดูแลระบบจะอนุมัติจากคิว alias และโมเดลจงใจตัดข้อมูลเพศ/อายุออกเพื่อความเป็นธรรม ซึ่งอาจอธิบายความแปรปรวนของเงินเดือนในบางตำแหน่งที่ตลาดเดิมกำหนดช่วงอายุไว้ได้น้อยลง

## 5.4 ข้อเสนอแนะสำหรับการพัฒนาต่อในอนาคต

1. **ขยายความครอบคลุมของแหล่งข้อมูล:** พัฒนาตัวดึงข้อมูลจากแหล่งที่สอง (**JobBKK** ตามลำดับแผน Could) และบูรณาการข้อมูลสถิติแรงงานรายเดือนของภาครัฐ (`dw.fact_labor_monthly`) จากธนาคารแห่งประเทศไทยและกรมการจัดหางานอย่างอัตโนมัติ เพื่อให้ภาพรวมตลาดสมบูรณ์ยิ่งขึ้น
2. **การเก็บข้อมูลอนุกรมเวลาระยะยาว (Multi-Year Longitudinal Tracking):** หากสถาบันการศึกษาสามารถรัน Pipeline Re-discovery รายสัปดาห์ต่อเนื่องเกิน 1–2 ปี จะทำให้มีข้อมูลเพียงพอสำหรับการวิเคราะห์ฤดูกาลการจ้างงาน (Seasonality) และต่อยอดสู่แบบจำลองพยากรณ์ความต้องการทักษะในอนาคต
3. **การปรับปรุงระบบคัดกรอง Alias และการจัดกลุ่มอาชีพ (Human-in-the-Loop):** ต่อยอดการจัดกลุ่มชื่อตำแหน่ง (`occupation cluster`) ด้วย TF-IDF + Clustering เพื่อตรวจทานความสอดคล้องของตำแหน่งงานใหม่ๆ ร่วมกับการทบทวนโดยผู้เชี่ยวชาญในหน้า Admin
4. **การเชื่อมโยงมาตรฐานหลักสูตรอุดมศึกษา (OBE / มคอ.):** พัฒนาฟังก์ชัน Export รายงานเปรียบเทียบทักษะในรูปแบบที่เชื่อมโยงกับผลลัพธ์การเรียนรู้ระดับหลักสูตร (PLOs) เพื่อให้อาจารย์นำไปใช้ประกอบเอกสารประกันคุณภาพการศึกษาและการปรับปรุงหลักสูตรได้โดยตรง
