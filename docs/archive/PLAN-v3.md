### 1.2 จุดที่ Gemini ขยายเกินจำเป็น
ระหว่างบทสนทนา ขอบเขตโตขึ้นทุกครั้งที่ถามต่อ จนเกินกำลังของโครงงานจริง:

| สิ่งที่ถูกเพิ่มเข้ามา | ปัญหา | ข้อเสนอ |
|---|---|---|
| เทียบคู่แข่ง 5 ระดับ รวม "แบรนด์ระดับโลก" และ "ปีนัง/กัวลาลัมเปอร์" | แบรนด์ระดับโลกแทบไม่มีใน 4 จังหวัด, KL ไกลจากบริบท | เหลือ 3 ระดับ: รัศมีใกล้ / เจ้าตลาดจังหวัด / chain ระดับประเทศ (ข้ามแดนเป็นส่วนเสริม) |
| ร้านทุกประเภทต้องกรอกต้นทุนทุก SKU + GP + ค่าแพ็กเกจ | ระบบว่างจนกว่าเจ้าของร้านจะกรอก, ใช้ได้จริงแค่ F&B | ทำเป็นโมดูลเสริม "เครื่องคิดกำไร" ไม่ใช่แกนหลัก |
| ML ทำนาย "ราคายุติธรรม" | มีข้อมูลราคาแค่ F&B บนแอปเดลิเวอรี ใช้กับอุตสาหกรรมอื่นไม่ได้ | ย้าย target ไปเป็นข้อมูลที่มีครบทุกร้าน (หัวข้อ 3.6) |
| Text-to-SQL, Gemini Vision ดึงเมนู, Gemini ติด label รีวิว | ขัดกับ R8 และกิน quota | ตัดออก ใช้ ML คลาสสิกแทน |
| มรสุมสองฝั่งทะเล (อ่าวไทย/อันดามัน) | พื้นที่นำร่องอยู่ฝั่งอ่าวไทยกับยะลาที่ไม่ติดทะเลทั้งหมด | ใช้ "ฤดูมรสุมเทียบนอกฤดู" + ปริมาณฝนจริง |
| ONNX ใน Vercel | ไม่จำเป็นเมื่อ Python deploy แยกได้ | Python service หรือคำนวณล่วงหน้าเก็บลงฐานข้อมูล |

### 1.3 เกณฑ์เลือกหัวข้อ
1. **ไม่ใช่ CRUD:** คุณค่าหลักต้องมาจากการประมวลข้อมูล ไม่ใช่การกรอกข้อมูล (R2)
2. **ถูกใจกรรมการสาย Data:** มีหลายแหล่งข้อมูล ต้องคลีนจริง มีคลังข้อมูล และ ML วัดผลได้ (R3, R4, R9)
3. **ข้อมูลหาได้จริงและพอ:** มีปริมาณพอสำหรับ ML 5–6 โมเดล และดึงซ้ำได้ (R5)
4. **ใกล้ตัว ภาคใต้ หลายผู้ประกอบการ** (R6, R7)
5. **ทำทันและ deploy ฟรีได้** (R1, R11)
6. **AI แชทลอยมีประโยชน์จริง** โดยไม่ต้องใช้ Text-to-SQL (R8)

## 2. หัวข้อที่เป็นไปได้

ทุกหัวข้อใช้ **โครงเดียวกัน** ได้ คือ scrape หรือดาวน์โหลดข้อมูล → คลีน → Data Warehouse → Dashboard → ML 6 โมเดล → Gemini แชทลอย → login หลายบทบาท ทำให้เปลี่ยนหัวข้อได้โดยไม่เสียแผนเทคนิค

### A. SouthBiz Pulse: วิเคราะห์คู่แข่งและทำเลสำหรับ SME 4 จังหวัดชายแดนใต้ ⭐ (หัวข้อเดิม ปรับขอบเขต)
- **ทำอะไร:** scrape ร้านค้าทุกประเภทจาก Google Maps (ตำแหน่ง, หมวด, เวลาเปิด, คุณลักษณะ, ดาว, รีวิว) และเมนู F&B จากแอปเดลิเวอรี แล้วบอกเจ้าของร้านว่า "ร้านฉันอยู่ตรงไหนเทียบคู่แข่ง ลูกค้าบ่นอะไร และควรปรับอะไร" ส่วนคนจะเปิดร้านใหม่ได้รู้ว่า "ทำเลไหนน่าเปิด"
- **ผู้ใช้:** เจ้าของร้าน, คนจะเปิดร้าน, admin
- **ML:** ทำนาย "ผลงานที่ร้านควรได้" จากทำเลและคุณลักษณะ (ใช้ได้ทุกอุตสาหกรรม) + จำแนก sentiment รีวิว
- **แชทลอย:** "ทำไมร้านฉันคะแนนต่ำกว่าที่คาด", "คู่แข่งในรัศมีนี้โดนบ่นเรื่องอะไร"
- **จุดเด่น:** ตรงสาขาคอมธุรกิจ, หลายธุรกิจตามที่ต้องการ, เดโมสวย (แผนที่ + dashboard), ใช้งานเอกสารและ design ที่ทำไว้ต่อได้
- **ความเสี่ยง:** scraper เปราะ (หน้าเว็บเปลี่ยน, โดน block), ขอบเขตกว้างถ้าไม่คุม

### B. SouthAgri Price Pulse: ระบบช่วยตัดสินใจขายยางพาราและพืชเศรษฐกิจภาคใต้
- **ทำอะไร:** รวบรวมราคายางพารา (และพืชอื่น เช่น ปาล์ม ทุเรียน ลองกอง) รายวันย้อนหลังหลายปี จากหน่วยงานทางการ (เช่น การยางแห่งประเทศไทย, สำนักงานเศรษฐกิจการเกษตร, Malaysian Rubber Board) รวมกับอัตราแลกเปลี่ยน ราคาน้ำมัน และฝนรายวัน แล้วพยากรณ์ราคา 1–30 วัน และแนะนำว่า "ควรขายตอนนี้หรือรอ"
- **ผู้ใช้:** เกษตรกรชาวสวน, สหกรณ์กองทุนสวนยาง, ลานรับซื้อ/พ่อค้าคนกลาง
- **ML:** พยากรณ์อนุกรมเวลา (baseline, SARIMAX, Random Forest, XGBoost, LightGBM, LSTM) ด้วย walk-forward validation
- **แชทลอย:** "ทำไมสัปดาห์หน้าราคาน่าจะขึ้น", "ฝนตกติดกันมีผลกับราคาแค่ไหน"
- **จุดเด่น:** ข้อมูลทางการและเสถียร ไม่ต้องห่วงเรื่อง ToS, อนุกรมเวลาเหมาะกับ DW มาก, ML วัดผลชัด, ใกล้ตัว (ยางคือรายได้หลักของ 4 จังหวัด), เชื่อมมาเลเซียได้ (ราคายางมาเลเซีย)
- **ความเสี่ยง:** ไม่ใช่ "หลายธุรกิจ" ตามที่ตั้งใจ, ราคาสินค้าโภคภัณฑ์พยากรณ์ยาก (ต้องรายงานเทียบ baseline ตรงๆ), ต้องตรวจก่อนว่าดาวน์โหลดย้อนหลังได้กี่ปี

### C. Deep South Edu Insight: วิเคราะห์คุณภาพการศึกษาระดับโรงเรียน 4 จังหวัดชายแดนใต้
- **ทำอะไร:** รวมผลสอบระดับชาติ ข้อมูลขนาดโรงเรียน ครู นักเรียนยากจน และที่ตั้ง แล้วหาโรงเรียนที่ "ทำได้ดีกว่าหรือแย่กว่าที่ควร" เพื่อจัดสรรการช่วยเหลือ
- **ผู้ใช้:** สำนักงานเขตพื้นที่การศึกษา, ผู้บริหารโรงเรียน (ใกล้กับสถานศึกษาที่คุณทำงาน)
- **ML:** ทำนายผลสอบเฉลี่ยของโรงเรียนจากปัจจัยแวดล้อม แล้วดูส่วนต่างจากผลจริง
- **จุดเด่น:** คุณค่าทางสังคมสูง, ไม่มีปัญหา PDPA ถ้าใช้ข้อมูลระดับโรงเรียน
- **ความเสี่ยง:** **ต้องตรวจก่อนว่ามีข้อมูลผลสอบระดับโรงเรียนให้ดาวน์โหลด** ถ้าได้แค่ระดับจังหวัด หัวข้อนี้จะอ่อนลงมาก, ตรงสาขาคอมธุรกิจน้อยกว่า

### D. Tourism & Border Pulse: เศรษฐกิจท่องเที่ยวและชายแดน 4 จังหวัด
- **ทำอะไร:** รวมสถิตินักท่องเที่ยวรายเดือน, รีวิวแหล่งท่องเที่ยว/ที่พัก, วันหยุดไทย-มาเลเซีย และฝน เพื่อวางแผนการตลาดท่องเที่ยว
- **ความเสี่ยง:** Gemini เคยเตือนไว้ถูกแล้วว่าสถิติรายเดือนมีแค่หลักร้อยแถว ไม่พอสำหรับ ML ถ้าเติมด้วยรีวิวก็จะกลายเป็นหัวข้อ A แบบแคบลง จึงแนะนำให้รวมเป็นส่วนหนึ่งของ A แทน

### E. Career & Workforce Intelligence (จาก `Career_Workforce_Intelligence_Project_Blueprint.md`)

**ฉบับเต็มตาม blueprint:** แพลตฟอร์มเชื่อมผู้หางาน, HR และสถานศึกษา + ETL + คลังข้อมูลตลาดแรงงาน + matching แบบอธิบายได้ + skill gap

**ขนาดจริงของฉบับเต็ม:** MVP 14 รายการ (หัวข้อ 5.1), 4 บทบาท, 4 dashboard, ตารางระบบงานราว 42 ตาราง (หัวข้อ 9) + ตารางคลังข้อมูล 11 ตาราง (หัวข้อ 8) **ใหญ่กว่าหัวข้อ A ราว 2 เท่าในส่วนเว็บแอป**

**จุดแข็ง:** เขียนรอบคอบกว่าเอกสารของ Gemini (เตือนเรื่อง license, ห้ามสร้างข้อมูลปลอมให้ครบจำนวน, ให้เริ่มจาก rule-based ก่อน ML), matching อธิบายเหตุผลได้, ตรงสาขาคอมธุรกิจ (HR), เชื่อมกับงานสถานศึกษาของคุณ

**ความเสี่ยงของฉบับเต็ม:**
1. **ครึ่งหนึ่งของ MVP คือระบบหางาน/สมัครงาน** (โปรไฟล์, ประกาศงาน, ใบสมัคร, สถานะ, สัมภาษณ์) ซึ่งเป็น CRUD และเป็นหัวข้อที่รุ่นพี่สายคอมธุรกิจทำบ่อย ขัดกับ R2 โดยตรง
2. **ข้อมูลที่เป็นหัวใจหาได้ยาก:** "ทักษะที่ตลาดต้องการ" ต้องมาจากประกาศงาน แต่ blueprint ไม่แนะนำให้ scrape ส่วนข้อมูลภาครัฐ (ธปท., กรมการจัดหางาน) เป็นตัวเลขรวมรายเดือน ไม่มีรายละเอียดทักษะ ทำให้ `fact_skill_demand` แทบว่าง
3. **ต้องมีผู้ใช้จริง 3 กลุ่มก่อนถึงจะมีข้อมูล:** ผู้สมัคร 20–30 คน, HR 5–10 คน, สถานศึกษา 3–5 แห่ง ทั้ง matching และการวัด Precision@K ต้องรอข้อมูลจากคนเหล่านี้
4. **แทบไม่มี ML ที่เทียบหลายโมเดล:** matching เป็น rule-based ส่วน ML อยู่ใน "ทำทีหลัง" ขัดกับ R9
5. **ESCO ไม่มีภาษาไทย:** ต้อง map ชื่อทักษะภาษาไทยเองทั้งหมด
6. **ขอบเขต "ทั้งประเทศ"** กว้างเกินไป และไม่ใช่ภาคใต้หรือ SME ตาม R6
7. **Stack ต่างจากที่วางไว้** (Vue + FastAPI + JWT แทน Next.js + Supabase) ต้องหา host สำหรับ backend เพิ่ม

**ฉบับปรับที่ทำได้ (E′): Southern Skill Demand Intelligence (data-first)**
- **ข้อมูล:** scrape ประกาศงานจากเว็บหางาน (อาจารย์อนุญาต) เน้นภาคใต้ + ข้อมูลกรมการจัดหางานรายเดือนรายจังหวัด
- **คลีน:** ดึงทักษะจากรายละเอียดงานด้วย dictionary + PyThaiNLP → map เข้า taxonomy ที่สร้างเอง (อ้างอิง O*NET/ESCO แล้วแปลไทย), normalize ตำแหน่งงานและเงินเดือน ("ตามตกลง", ช่วงเงินเดือน)
- **คลังข้อมูล:** `fact_job_posting`, `fact_posting_skill`, `fact_labor_monthly` + dim ตำแหน่ง/ทักษะ/บริษัท/พื้นที่/วันที่
- **ML:** ทำนายเงินเดือนจากตำแหน่ง ทักษะ ประสบการณ์ และพื้นที่ (6 โมเดล + baseline) + จำแนกหมวดงานจากข้อความประกาศ (3–4 โมเดล)
- **ผู้ใช้:** นักศึกษา/ผู้จบใหม่ (ใส่ทักษะของตัวเอง → เห็น skill gap, งานที่ตรง, เงินเดือนที่คาด), สถานศึกษา (เทียบทักษะของหลักสูตรกับตลาด), admin
- **ตัดออก:** ใบสมัคร, pipeline สรรหา, สัมภาษณ์, บริษัทลงประกาศเอง, ระบบติดตามการเรียน
- **แชทลอย:** "ทักษะไหนกำลังเป็นที่ต้องการในสงขลา", "ฉันขาดอะไรสำหรับงาน data analyst"
- **ความเสี่ยงที่เหลือ:** ประกาศงานในยะลา ปัตตานี นราธิวาสน่าจะมีน้อย อาจต้องใช้ข้อมูลทั้งภาคใต้หรือทั้งประเทศเพื่อให้ ML มีข้อมูลพอ และเว็บหางานก็เปลี่ยนหน้าเว็บหรือ block ได้เหมือน Google Maps

- **เลือก A** ถ้ายอมรับงาน scraper ที่หนักและอยากได้หลายธุรกิจตามที่ตั้งใจ (ตรงโจทย์ที่สุด และใช้งานที่ทำไว้ต่อได้)

### 3.5 Data Warehouse (Galaxy Schema แบบพอดี)
- **Dimensions (ใช้ร่วมกัน):** `dim_date` (วันหยุดไทย/มาเลเซีย, รอมฎอน, ฤดูมรสุม), `dim_geography` (จังหวัด/อำเภอ/ลักษณะพื้นที่), `dim_category` (Industry Pack: 5 กลุ่ม + ป้ายและหน่วยตามอุตสาหกรรม), `dim_brand` (อิสระ/chain), `dim_outlet` (ร้าน + พิกัด + คุณลักษณะ), `dim_aspect`, `dim_source`
- **Facts:**
  - `fact_review`: grain = 1 รีวิว (ดาว, ภาษา, sentiment)
  - `fact_review_aspect`: grain = 1 รีวิว × 1 aspect (แยกออกมากันการนับซ้ำ)
  - `fact_outlet_monthly`: grain = 1 ร้าน × 1 เดือน (จำนวนรีวิวสะสม, รีวิวใหม่, ดาว, ดัชนีความนิยม, เป็นเจ้าตลาดไหม)
  - `fact_menu_price`: grain = 1 เมนู × 1 ร้าน × 1 รอบเก็บ (F&B)
  - `fact_weather_daily`: grain = 1 อำเภอ × 1 วัน
- **ตารางส่วนตัว (RLS):** `app_profile`, `app_sku`, `app_watchlist`, `app_pins`, `app_chat_log`
- **ML:** `ml_experiment` (ผลทุกโมเดลทุก fold), `ml_prediction` (ค่าคาดของทุกร้าน + คะแนนทำเลราย hex)
- **บทเรียนจาก v2 ที่ต้องทำตั้งแต่ migration แรก:** แยก schema (`staging`, `dw`, `mart`, `public` สำหรับ `app_*`) และเปิด RLS ทุกตารางใน `public` (ดูรายละเอียดใน PLAN-v2 หัวข้อ 6)

### 3.6 Machine Learning
**งานที่ 1: ทำนายผลงานที่ร้านควรได้ (Regression, 6 โมเดล + baseline)**
- **Target:** ดัชนีความนิยม = log(1 + จำนวนรีวิวต่อเดือนนับจากรีวิวแรก) ใช้วันที่ของรีวิวแรกแทนอายุร้าน ทำให้ร้านเก่าและร้านใหม่เทียบกันได้ และ **มีค่านี้ครบทุกร้านทุกอุตสาหกรรม**
- **Features:** หมวด, อำเภอ, ลักษณะพื้นที่, ระยะถึงตัวเมือง/มหาวิทยาลัย/ด่านชายแดน/แหล่งท่องเที่ยว, จำนวนคู่แข่งหมวดเดียวกันใน 1 กม., ความหนาแน่นร้านรอบข้าง, ชั่วโมงเปิดต่อสัปดาห์, เปิดเช้า/ดึก, ปิดช่วงละหมาดวันศุกร์, ตราฮาลาล, ที่จอด, Wi-Fi, มีบนแอปเดลิเวอรี, ช่วงราคา, เป็น chain ไหม
- **ห้ามใช้เป็น feature:** ดาวและจำนวนรูป (สัมพันธ์กับ target โดยตรง)
- **โมเดล:** Ridge, KNN หรือ SVR, Random Forest, XGBoost, LightGBM, CatBoost + baseline (ค่ามัธยฐานของหมวดในอำเภอ)
- **การวัดผล:** 5-fold GroupKFold (group = แบรนด์ กันสาขา chain รั่วข้าม fold) + ทดสอบแยกตามอำเภอ, R², RMSE, MAE, MAPE, SHAP
- **นำไปใช้:**
  - **Performance Gap:** ผลจริงเทียบค่าคาด เช่น "ร้านคุณได้ต่ำกว่าที่ร้านทำเลและคุณลักษณะแบบนี้ควรได้ 33%"
  - **คะแนนทำเล:** ใส่พิกัดหมุด + สิ่งที่ตั้งใจจะมี ระบบให้ค่าคาด + เหตุผล
- **ข้อจำกัดที่ต้องเขียนในเล่ม:** จำนวนรีวิวไม่ใช่ยอดขาย ร้านที่นักท่องเที่ยวไปเยอะจะได้รีวิวมากกว่า

**งานที่ 2: จำแนก sentiment รีวิว (Classification)**
- **Label ฟรีจากดาว:** 1–2 ดาว = ลบ, 4–5 ดาว = บวก (3 ดาวแยกเป็นกลาง หรือไม่นำมาเทรน)
- **โมเดล:** Naive Bayes, Logistic Regression, Linear SVM (บน TF-IDF แบบ char n-gram เหมาะกับภาษาไทยที่ไม่เว้นวรรค)
- **Aspect:** แบ่งประโยค + dictionary คำต่อ aspect (เช่น "รอนาน/คิว" → ความเร็ว, "จอดรถ" → ที่จอด) ตาม Industry Pack
- **ภาษา:** ใช้ library ตรวจภาษา + กฎเสริมสำหรับมลายูที่เขียนด้วยอักษรไทย
- **ตรวจคุณภาพ:** สุ่ม 200 รีวิวมาอ่านเอง เพื่อดูว่า label จากดาวคลาดเคลื่อนแค่ไหน

**Deploy:** เทรนบนเครื่องหรือ Colab แล้วคำนวณค่าคาดของทุกร้านและทุก hex เก็บลง `ml_prediction` ล่วงหน้า (หน้าเว็บอ่านจากฐานข้อมูลทันที) ส่วนคะแนนหมุดใหม่เรียก Python service (FastAPI บน Hugging Face Spaces) ถ้า service ไม่ตอบจะใช้ค่าของ hex ที่หมุดอยู่แทน

- จำกัดจำนวนคำถามต่อผู้ใช้ต่อวัน เพื่อกันใช้ quota หมด

- แจ้งใน privacy notice ว่าข้อมูลบนหน้าจะถูกส่งให้ Google ประมวลผล

### 3.10 การทดสอบและประเมินผล (รูปแบบโครงงาน)
| หัวข้อ | วิธี |
|---|---|
| ฟังก์ชันระบบ | ตาราง test case ทุก use case + ทดสอบ E2E flow หลัก |
| ข้อมูล | จำนวนร้าน/รีวิวต่อจังหวัด, % ข้อมูลครบ, % ซ้ำ, ผลตรวจคุณภาพข้อมูล |
| ML | ตารางเทียบ 6 โมเดล + baseline (R², RMSE, MAE, MAPE), SHAP, ผล sentiment (accuracy, F1) |
| แชท | ชุดคำถาม 30 ข้อ ตรวจว่าตอบตรงกับข้อมูลบนหน้า และไม่แต่งตัวเลข |
| ความพึงพอใจ | แบบสอบถาม Likert 5 ระดับ (x̄, S.D.) จากผู้ทดลองใช้ตามจำนวนที่อาจารย์กำหนด |

### 3.12 ความเสี่ยงและทางแก้
| ความเสี่ยง | ทางแก้ |
|---|---|
| Scraper โดน block หรือหน้าเว็บเปลี่ยน | scrape ช้าๆ, resume ได้, selector อยู่ไฟล์เดียว, scrape ข้อมูลหลักให้เสร็จเร็ว (สัปดาห์ 3–5) แล้วเก็บ snapshot ไว้ ถ้าเจอ CAPTCHA ให้หยุด ไม่หลบเลี่ยง |

| PDPA | ไม่เก็บชื่อ/รูป/ลิงก์ผู้รีวิว, ลบเบอร์โทรในเนื้อหา, หน้าให้ร้านขอนำข้อมูลออก, หนังสืออนุมัติจากอาจารย์ |
